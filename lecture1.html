Chapter 1 · Guided lecture

From one computer to coordinated independent computers

A distributed system is not merely “many computers.” It is a collection of independent computers that communicate, coordinate, and collectively provide a service. The important design challenge is that each computer has its own memory, clock, resources, and possible failures.

1. What is a distributed system?

Plain explanation: Imagine several computers working as a team. Each computer can perform tasks independently, but the computers exchange messages so that users experience one coordinated service.

Technical explanation: A distributed system consists of autonomous computing nodes connected by a network. The nodes coordinate actions through communication protocols, divide work, exchange data, and attempt to present a coherent service despite network delay and partial failure.

Independent

Each node owns its processor, memory, operating system, and local clock.

Nodes exchange messages through a network rather than reading one shared physical memory.

Coordinated

Nodes follow protocols so their separate actions contribute to a common service.

Why this matters: Independence gives scalability and resilience, but it also introduces delay, uncertainty, and the possibility that only part of the system fails.

2. Why do we need distributed systems?

Scale

One computer has finite CPU, memory, storage, and network capacity. Distribution lets a system combine the capacity of multiple machines.

Responsiveness

Work and copies of data can be placed closer to users, reducing the distance requests travel.

Availability

Replicas may allow service to continue when one component becomes unavailable.

Parallel work

A large task can be divided into smaller tasks that different computers process at the same time.

Example: processing a large dataset

Suppose one server needs 10 hours to process a collection of independent files. If the work can be divided safely among several workers, multiple files can be processed concurrently. The speedup will not necessarily be perfect: coordination, data transfer, uneven tasks, and failures create overhead.

Important: Adding machines does not automatically make an application faster. The software and data must be partitionable, and communication overhead must remain manageable.

4. Core features of distributed systems

A variable stored in Node A’s RAM cannot be read directly by Node B as if it were a local variable. Information must be encoded, transmitted, received, decoded, and interpreted.

Nodes communicate through messages: requests, replies, events, heartbeats, updates, and acknowledgements. Messages can be delayed, duplicated, reordered, corrupted, or lost unless protocols address these risks.

Several nodes execute at the same time. Their operations may overlap, creating race conditions when they read or update related data.

One node or network path may fail while the rest of the system continues. A client may know that a response did not arrive but may not know whether the remote operation ran.

Key design lesson: local programming assumptions—instant access, one memory, one clock, and one failure boundary—do not hold across a network.

5. Physical clocks and event ordering

Each node has a hardware clock. Even after synchronization, clocks do not advance at exactly the same rate; this is called clock drift. At a particular instant, their displayed times may differ; this is clock skew.

Node A
10:00:00.120
Send M
Network
variable delay
Node B
09:59:59.940
Receive M

If we compare only the timestamps above, the receive event appears earlier than the send event. The problem is not that causality reversed; the clocks disagree. Network delay also varies, so a receiver cannot infer an exact send time from arrival time.

Safe reasoning: A message must be sent before it is received. This causal relationship is more dependable than comparing unsynchronized physical timestamps.

Thought experiment

Node A records payment approval at 12:00:00.200. Node B records order shipment at 12:00:00.100. Did shipment happen first? Not necessarily. Before answering, we need to know clock error and the messages connecting the events.

6. Parallel computing versus distributed computing

AspectParallel systemDistributed system
Typical placementMultiple processors/cores, often in one tightly coupled machineIndependent computers connected by a network
MemoryMay use shared physical memoryNormally separate physical memory per node
CommunicationShared memory or high-speed interconnectNetwork message passing
Clock/failure boundaryOften more tightly controlledSeparate clocks and partial failures
Main emphasisPerform computations simultaneouslyCoordinate autonomous networked components

The categories can overlap. A distributed cluster may perform parallel computation, and each cluster node may itself contain parallel CPU cores. The distinction is about architecture and assumptions, not simply whether tasks happen at the same time.

Common exam trap: “Uses multiple processors” alone does not prove that a system is distributed. Ask whether the processing units are independent computers with separate memory communicating over a network.

8. Worked design scenario

Scenario

A university learning portal runs on one server. During exam week, thousands of students log in simultaneously. Pages become slow, and a server restart makes the whole portal unavailable.

Reasoning

  1. Identify constraints: the single server has finite CPU, RAM, connection capacity, and one failure boundary.
  2. Short-term option: vertical scaling could add CPU and RAM, but it does not remove the physical ceiling or single-server dependency.
  3. Scale-out option: place several application servers behind a load balancer.
  4. State challenge: if session data lives only in one application server’s memory, another server cannot see it. Sessions need a shared/distributed store or an appropriate stateless design.
  5. Data challenge: database capacity, replication, and consistency must be designed separately.
  6. Failure handling: health checks should stop routing requests to an unavailable server.

Conclusion: Horizontal scaling can improve capacity and availability, but only when state, data, routing, and failures are explicitly designed for multiple independent nodes.

9. Common misconceptions

“Many cores means distributed.”

Not necessarily. One multicore machine may be parallel but not distributed.

“More servers always means faster.”

Coordination and communication can outweigh the benefit if work cannot be divided efficiently.

“A timeout means the operation failed.”

A reply may be delayed or lost after the operation succeeded.

“Clock synchronization gives one perfect time.”

Clocks still drift and synchronization has bounded error.

“Replication automatically gives consistency.”

Copies require an update and conflict strategy.

“Distribution hides every failure.”

Good abstractions help, but partial failures still influence correctness and user experience.

Lecture summary

  • A distributed system uses independent computers that coordinate through network messages.
  • Distribution supports scale, geographic reach, parallel work, and—when properly designed—resilience.
  • Vertical scaling strengthens one machine; horizontal scaling adds machines.
  • Separate physical memory means nodes must communicate explicitly.
  • Separate drifting clocks and variable network delay make event ordering difficult.
  • Parallel and distributed computing overlap, but they rely on different architectural assumptions.
  • The Netflix example illustrates nearby replicas and coordinated service selection.
